A portfolio should feel personal, fast, and easy to evolve. I wanted a setup where writing a new post felt as simple as opening a folder, creating an `index.mdx` file, and shipping. Astro gave me the performance baseline, while MDX gave me the flexibility to mix content with small interactive components when a plain paragraph was not enough.

## Why Astro and MDX fit together

Astro lets me keep the public site **static by default**, which keeps deploys simple and performance excellent. MDX adds the missing layer: the ability to write long-form content with familiar Markdown syntax while still embedding custom UI when I need richer explanations.

> The sweet spot for a personal site is a stack that stays boring for content and powerful for edge cases.

A good authoring system should make these tasks easy:

- Drafting and publishing new posts quickly
- Reusing callouts, image blocks, and code snippets
- Keeping metadata structured and type-safe
- Generating RSS and a sitemap automatically

### The workflow I was aiming for

1. Create a folder under `src/content/blog/`
2. Add frontmatter for title, summary, and dates
3. Write in Markdown first
4. Drop into MDX only when a richer component helps the story

#### Small details matter

Even little features like tag pills, heading links, and reading-time estimates make a blog feel more complete. They are easy to skip at the beginning, but they pay off once the number of posts grows.

<Callout type="note">
	Structured content collections are a huge upgrade over loose Markdown files
	because they catch bad metadata before a post ever reaches production.
</Callout>

## Content collections keep the system honest

Astro content collections add a schema layer around content. That means dates are coerced correctly, optional fields are explicit, and drafts are easy to filter out during builds.

```ts {6-14}
// src/content.config.ts
import { glob } from 'astro/loaders';
import { defineCollection } from 'astro:content';
import { z } from 'astro/zod';

const blog = defineCollection({
	loader: glob({ pattern: '**/*.{md,mdx}', base: './src/content/blog' }),
	schema: z.object({
		title: z.string(),
		description: z.string(),
		publishDate: z.coerce.date(),
		tags: z.array(z.string()).default([]),
		draft: z.boolean().default(false),
	}),
});

export const collections = { blog };
```

The nice part is that this pattern scales. Today it is just a blog, but later it could support case studies, changelogs, or notes using the same approach.

<Callout type="tip">
	If a field might eventually be derived automatically, such as reading time,
	keep it optional in the schema and compute it as a fallback in the page layer.
</Callout>

## Styling content without losing control

Raw Markdown is useful, but it rarely matches the rest of a design system without a little work. I prefer styling a dedicated content wrapper instead of depending on generic defaults. That makes it clear how lists, blockquotes, tables, and code should look in both light and dark themes.

Here is a quick comparison:

| Concern     | Plain Markdown     | Styled MDX system                 |
| ----------- | ------------------ | --------------------------------- |
| Headings    | Browser defaults   | Branded scale and spacing         |
| Tables      | Bare HTML table    | Responsive, bordered, readable    |
| Code blocks | Functional         | Syntax highlighted and consistent |
| Media       | Unstyled image tag | Framed image with captions        |

Inline emphasis also matters. You should be able to mix **strong statements**, _softer nuance_, and `inline code` naturally inside normal paragraphs.

## Syntax highlighting and reusable code blocks

Astro's built-in syntax highlighting is enough for most examples. When I need a more editorial code presentation, a custom MDX component gives me a filename header and copy button.

```ts filename="src/lib/remark-reading-time.ts"
import { toString as mdastToString } from 'mdast-util-to-string';
import getReadingTime from 'reading-time';
import type { Root } from 'mdast';
import type { VFile } from 'vfile';

export function remarkReadingTime() {
	return function (tree: Root, file: VFile) {
		const text = mdastToString(tree, { includeImageAlt: false });
		const { text: readingTime } = getReadingTime(text);
		const astroData = (file.data.astro ?? {}) as {
			frontmatter?: Record<string, unknown>;
		};
		astroData.frontmatter = { ...astroData.frontmatter, readingTime };
		file.data.astro = astroData;
	};
}
```

This remark plugin runs once at build time during AST traversal. `mdast-util-to-string` extracts only real prose — headings, paragraphs, list items — skipping JSX tags, imports, and component props that would inflate a naive word count on `post.body`.

That split works well in practice: fenced blocks for everyday snippets, and a richer `CodeBlock` component when presentation matters.

<Callout type="danger">
	A blog can look finished while still being fragile. If build, lint, and
	formatting do not pass, the system is not done yet.
</Callout>

## Final thoughts

A modern portfolio blog should support writing first and tooling second. Once the foundation is in place, publishing becomes a lightweight habit instead of a mini project every time.

The result I wanted was simple:

- Fast static pages
- Type-safe content metadata
- Reusable MDX building blocks
- Automatic discovery via RSS and sitemap

If the system makes publishing easier next month than it was today, then it is doing its job.
